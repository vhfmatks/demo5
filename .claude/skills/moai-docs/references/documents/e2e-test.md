# `docs/e2e-test.md` — 어떻게 시험했고, 무엇이 확인됐나요?

단위·API/UI E2E 계획·TC·실행 결과·자동 현황·근거를 작성하거나 대조할 때만 읽는다. AC 판정·변경 영향은 [라이프사이클](../lifecycle.md), 시험 구현·격리 실행은 프로젝트 `docs/conventions/testing.md`의 필요한 절만 읽는다. 기존 문서의 TC·실행 이력·자동 마커는 보존한다.

**작성·갱신 시점:** 구현 전 요구별 시나리오를 적고, 시험 후 명령·소스 SHA·실제 결과·로그와 화면 경로를 채운다. 다른 사람이 재현할 수 있도록 README의 실행 순서와 연결한다.

**본문 배치:** 기존 자동 현황 영역은 보존하고, 수기 본문은 다음 절 순서로 작성한다.

- `## 1. 재현 환경 · 명령`: 환경·정확한 버전·합성 데이터·설치·빌드·기동·시험·종료·정리 명령과 실행 범위를 적는다.
- `## 2. 시나리오`: REQ · AC → 핵심 로직 단위 시험 / 사용자 흐름 E2E · TC를 연결하고 정상·오류·권한·저장 후 재조회 경계를 계획한다. 표 열은 `TC | REQ | AC | 경계 | GIVEN · WHEN · THEN | 예상 결과 | 자동화 위치`다. 실제 결과는 이 계획 표에 섞지 않는다.
- `## 3. 실제 실행 결과`: `실행 ID | 명령·범위 | 실행 환경 | 소스 SHA | 실행 시각 | PASS/FAIL/SKIP | 미실행·미검증 | 근거 경로`로 기록한다. 단위 시험과 API/UI E2E 결과를 구분하고 기존 실행 이력을 유지한다.
- `## 4. 근거 보관과 한계`: 로그·화면·보고서 링크, 실패·SKIP·미실행·미검증 사유, 제약·재시험·남은 확인을 적는다.

`<!-- e2e-dashboard:start -->`·종료 마커 사이 현황은 `npm run e2e:dashboard`로 생성하고 직접 수정하지 않는다. 연결된 현황 열은 `REQ | AC | TC | 경계 | 시험 파일(E2E · 단위) | 결과 | 소스 SHA | 실행 시각(UTC) · 근거 | 실행 환경 | 이력`이다. 이 레이아웃 안내로 runner·현황 스키마·기존 TC를 임의로 바꾸지 않는다.

예시 계획 — 타인의 자료는 열리지 않아야 한다(실제 요구·TC ID로 치환하며 실행 결과가 아님):

```text
REQ-01 → 구현: 권한 검사 → 검증: TC-DOMAIN-API-001
GIVEN 사용자 A가 로그인한다
WHEN 사용자 B의 자료를 직접 요청한다
THEN 요청 거부 + 자료 유출 없음
AND 저장 데이터가 바뀌지 않는다

실행 명령 / 예상 결과 / 실제 결과 / 근거 경로
상태: 미실행 — 직접 실행한 뒤 기입
```

HTTP 200이나 테스트 파일의 존재만으로 기능 성공을 증명할 수 없다. 정상·오류·권한 경계·저장값을 실제로 확인하고, 모든 필수 TC의 결과로 AC 판정은 PRD에 반영한다.

## 시험 계획과 결과 연결

- `docs/e2e-test.md` §2는 `TC | REQ | AC | 경계 | GIVEN · WHEN · THEN | 예상 결과 | 자동화 위치` 계약을 따른다. REQ↔AC와 TC 제목·파일을 대조하고 단위 seam이면 `tests/unit/<x>.test.ts`도 연결한다. 예상과 실제 결과는 서로 다른 곳에 둔다.
- TC 고르기(G2): `.claude/skills/moai-kit/references/test-patterns.md` §1–§2로 규칙마다 API TC 하나(거부는 저장값 불변 확인), 사용자 흐름 AC마다 UI TC 하나. REQ = 그 AC의 REQ(`AC-01-1` → `REQ-01`). 모든 AC는 정상 경계를, 규칙에 해당 경계가 있으면 오류·권한·재조회도 덮는다(빠지면 계획 공백이니 G2에서 채운다). GIVEN · WHEN · THEN 끝에 `AND <부수 효과>`를 둘 수 있다. 보안 TC는 이름 끝에 `(SEC-…)`. 자동화 위치 = 계획한 `tests/e2e/<x>.api|ui.spec.ts`(기존 파일을 확장하면 그 파일) + 티켓 TDD seam이 단위 시험이면 ` · tests/unit/<x>.test.ts`.
- E2E ID는 `TC-DOMAIN-API/UI-NNN` 규칙에 따라 실제 DOMAIN과 API 또는 UI를 사용한다. 기존 ID를 재사용·재번호화하지 않고, 단위 시험에 임의 API/UI ID를 강요하지 않는다. 사용자 흐름은 UI, 서버 규칙·거부·저장 결과는 API, 공개 정책/서비스의 핵심 로직은 단위 시험으로 구분한다.
- 경계는 정상·오류·권한·재조회 중 실제 확인하는 것을 적는다. 한 AC가 거부 전용이면 해당 거부 경계를 시험하고 정상 성공은 대응 허용 AC/TC로 연결한다. 거부는 응답뿐 아니라 자료 유출 없음·저장값 불변을 확인한다. 저장 동작은 후속 조회·새로고침으로 확인한다.
- `npm run lint:contracts`는 ID·파일·REQ/AC·경계의 형식을 대조한다. 사람이 시나리오·assertion이 AC를 실제 증명하는지도 확인한다. 형식 통과를 동작 PASS로 쓰지 않는다.
- 현황 블록은 `npm run e2e:dashboard`가 `docs/evidence/<runId>.md`와 `docs/evidence/unit-*.md`에서 생성한다. 자동 영역은 직접 수정하지 않는다. 단위 근거는 지원되는 프로젝트에서 `npm run test:unit:evidence`로 남긴다. 전체 단위 PASS만으로 개별 AC·TC가 통과했다고 추정하지 않는다.
- 실행 중 소스 변경·dirty·0개·불완전한 보고서·SKIP·FLAKY는 그대로 표시한다. 시험 SHA를 현재 HEAD로 바꾸지 않고 기존 runner의 소스 해시·manifest를 사용한다. 새로운 자체 해시 규칙을 만들지 않는다.
