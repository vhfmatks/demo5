# `docs/prd.md` — 무엇이 되면 완성인가요?

PRD의 요구·AC·연결·판정을 작성·대조할 때만 읽는다. REQ·AC·TC 연결 또는 상태를 변경할 때만 [라이프사이클](../lifecycle.md)을 추가로 읽는다. 기존 문서의 ID·결정·실행 이력은 보존한다.

**작성·갱신 시점:** 구현 전 요구와 확인 조건을 정하고, 바뀌면 이유·Issue·시험을 함께 고친다. 구현·실행 후 AC별 상태를 갱신한다.

**본문 배치:** 출처·필수 / 추가 / 미완료 구분 → REQ 요구와 AC 인수조건 → FLOW·Issue·TC 연결 → 권한·데이터·상태 규칙 → 변경 이유·영향·실제 판정 근거.

- 요구 표: `REQ | 출처 | 요구 | AC | Issue | PR | TC | 상태`. 기존 표가 범위 구분을 담지 않으면 요구 본문이나 범위 열로 명시한다.
- AC별 연결·판정 표(필수, `## AC별 연결·판정`): `AC | 인수조건 | FLOW | Issue/PR | TC | 상태 | 판정 근거`. REQ 행에 적은 AC마다 한 행이며 AC 상태의 원본이다. FLOW는 experience 흐름 표의 `FLOW-NN`, 연결 전 `미정`, 사용자 흐름이 없는 서버 규칙은 `—`. TC는 e2e-test §2에서 그 AC를 덮는 계획 TC 전체 ID(축약 금지).
- `npm run lint:contracts`가 대조한다: REQ·AC 상태 형식, 빠진 AC 행, TC = §2 계획, FLOW ID 존재, `검증(<sha7>)`의 그 SHA 미커밋 아닌 PASS 근거, 실행 근거가 있는데 `미실행`인 행. 상태에 설명을 붙이지 않고(`검증(미커밋…)` 금지) 설명은 판정 근거 칸에 둔다.

REQ-01 → AC-01-1의 조건은 "저장 후 새로고침해 같은 내용 확인"처럼 관찰 가능한 행동으로 쓴다. grill은 요구·AC를 확정하고, spec은 Issue·TC를 연결하며, docs는 실제 결과를 판정한다. 일부 AC만 PASS이면 REQ 전체를 검증으로 표시하지 않는다. 시험 표·TC 파일·실행 결과를 변경할 때만 [e2e-test](e2e-test.md)를 추가로 읽는다.
