# `docs/project-brief.md` — 무엇을, 누구를 위해 만드나요?

brief의 범위·선택 이유·가치·팀 역할을 작성·갱신할 때만 읽는다. 제공된 문서 레이아웃을 따르고 기존 문서의 결정·REQ·실행 이력은 보존한다.

**작성·갱신 시점:** 주제 공개 후 문제·사용자·범위를 정하고, 개발 뒤 실제 결과로 갱신한다. 범위·역할 변경의 이유도 남긴다.

**본문 배치:** 문제·대상 사용자 → 필수 / 추가 / 제외와 실제 구현 상태 → 선택 이유·관찰한 가치 / 예상 효과 → 팀원 3명의 역할·변경 이유·제약.

- 범위 표: `구분 | REQ 또는 제외 항목 | 선택 이유 | 실제 구현 상태 | 근거`.
- 효과 표: `관련 범위 | 예상 효과 | 확인 방법·비교 대상 | 관찰한 가치 | 근거·한계`.
- 팀 역할 표: `팀원 | 현재 역할 | 작업·리뷰·기여 근거 | 변경 이유 | 제약`.

요구·범위는 grill 결정, 실제 구현 상태는 PRD의 AC 판정, 관찰 가치는 experience 근거를 요약한다. 기능 시험을 사용자 효과의 실측으로 바꾸지 않는다. 상세 AC 판정·상태를 바꿀 때만 [라이프사이클](../lifecycle.md)을 추가로 읽는다.
