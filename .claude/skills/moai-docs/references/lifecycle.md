# REQ → AC → TC 라이프사이클

REQ·AC·시험 연결, 상태 판정, 요구·코드·정책 변경의 영향 분석·재시험을 다룰 때만 읽는다. 문서 한 개의 레이아웃만 정리할 때는 읽지 않는다. 문서별 형식은 해당 `documents/` 파일을 선택한다.

```text
문제·범위 → REQ → AC → FLOW·Issue → 구현 코드 → 단위/API·UI E2E TC
→ 실행 환경·명령·소스 SHA·PASS/FAIL/SKIP·근거 → AC 판정 → 8종 문서 갱신
                                 변경·실패 → 영향 분석 → 미검증 → 재시험
```

| 단계 | 작성·대조할 연결 | 다음 단계 조건 |
|---|---|---|
| 요구 확정(G1) | brief의 필수/추가/제외·출처 → PRD의 REQ·AC. `REQ-01`의 조건은 `AC-01-1`처럼 기존 번호 체계를 따른다 | 요구·권한·저장·상태·거부 결과가 관찰 가능하고 사용자 확인이 있음 |
| 흐름·계획(G2) | AC → experience의 FLOW·arch의 구현 경계 → Issue의 Test seam·TDD seam → e2e-test §2의 TC·단위 시험 파일 | 필수 AC마다 시험이 있고 정상·오류·권한·재조회 적용 경계가 빠지지 않음 |
| 구현·리뷰(G3–G4) | Issue → PR·변경 코드 → 실제 RED/GREEN·좁은 검증·리뷰·수정 근거. SEC도 코드·TC로 연결 | 계획 ID·파일·시험 제목이 일치하고 유예·미검증이 명시됨 |
| 통합 시험(G6) | 같은 후보 소스의 단위·격리 API/UI E2E → SHA·시각·명령·실제 결과·근거 | 모든 필수 TC·경계가 실제 통과한 AC만 검증, 실패·SKIP·미실행은 남김 |
| 반영·릴리스(G7–G8) | 결과 → PRD AC·REQ → brief 실제 범위·experience·SEC·development → README 근거 링크 | 시험 C → D 변경 범위가 문서·근거뿐이고 제출 소스에 필요한 파일이 있음 |
| 변경·회귀(수시) | 변경 이유 → 영향 REQ·AC·FLOW·SEC·코드·TC·문서 → 재시험 | 과거 결과는 이력으로 유지하고 현재 영향 항목을 재검증한 뒤 상태 갱신 |

## 시험 계획과 결과 연결

TC ID·경계·계획 표·현황·실행 근거를 작성하거나 대조할 때만 [e2e-test 매뉴얼](documents/e2e-test.md)의 "시험 계획과 결과 연결"을 추가로 읽는다. 라이프사이클 연결을 확인한다는 이유로 다른 문서 매뉴얼 전부를 읽지 않는다.

## 변경·회귀 처리

1. 범위·요구 변경은 이유·결정 근거를 남기고 grill의 확인을 거쳐 REQ·AC를 고친다. 기존 ID는 유지하며 새로운 독립 요구만 새 번호를 쓴다. spec의 Issue·Test/TDD seam·TC 계획과 FLOW·SEC·설계도 함께 맞춘다.
2. 코드·시험·설정·정책 변경의 영향 REQ·AC·TC와 읽는 공유 계약을 확인한다. 종속·회귀 범위를 빠뜨리지 않고, 영향받는 검증 상태는 `미검증`으로 되돌린다. 과거 결과·SHA·실행 이력은 삭제하지 않는다.
3. 실패는 TC·예상/실제·명령·SHA·근거를 먼저 기록한다. 기존 Issue·버그와 중복 확인 후 승인된 tracker 절차로 연결하고, 개발 이력에 수정·재시험을 남긴다. docs 모드에서 기능 코드를 고치지 않는다.
4. 관련 단위·API/UI부터 재시험하고 통합 후보 최종 게이트를 다시 수행한다. 새 근거로 AC·REQ·SEC 상태와 8종의 영향 부분만 갱신한다.
