# 최종 시험·제출 근거 확정

## final (G6–G8, 릴리스)

[라이프사이클](../lifecycle.md)과 [audit 절차](audit.md)를 읽고 대상 범위·필수 AC를 먼저 확인한다. 문서별 매뉴얼은 아래 단계에서 실제 수정·대조할 때 한 개씩 로드한다. 최종 제출은 모든 문서를 확인하지만 전체 매뉴얼을 처음부터 한 번에 읽지 않는다.

1. 시험 대상 코드·시험·설정이 커밋되고 트리가 깨끗할 때 **C**를 `git rev-parse HEAD`로 고정한다. 미커밋 변경이 있으면 보존하고 최종 제출 검증으로 표시하지 않는다. 최종 검증은 `npm run verify` → 프로젝트가 지원하면 `npm run test:unit:evidence` → `npm run test:e2e` → `npm run evidence` 순으로 실행한다. E2E는 격리 runner만 사용하고 명령·종료코드·건수·환경·시각·소스 SHA를 기록한다.
2. 실패·SKIP·FLAKY·불완전 실행도 실제 근거를 보관하고 상태를 반영한 뒤 릴리스 진행을 멈춘다. 기능 코드는 여기서 고치지 않고 담당 구현으로 돌린다. 수정 후 후보 소스를 다시 고정해 재시험한다. 성공 실행만 남기거나 실패를 지우지 않는다.
3. 필요한 보고서·합성 데이터 화면은 `docs/evidence/<runId>/`에 보관하고 runId·SHA 연결을 확인한다. `docs/e2e-test.md`는 `npm run e2e:dashboard`로 현황을 재생성하고 §3에 C·명령·시각·환경·전체 건수·근거를 적는다. 단위 전체 결과와 개별 TC·AC 근거를 구분한다.
4. `docs/prd.md`는 같은 후보에서 모든 필수 TC·적용 경계가 통과한 AC만 `검증(<C7>)`으로 판정한다. 나머지는 실패·미검증·미실행·미구현으로 남긴다. `docs/security-compliance.md`에는 SEC별 정상·거부·저장값 결과를 연결한다. 검증된 TC 하나로 REQ 전체를 검증하지 않는다.
5. brief는 실제 제공 범위·AC 판정·관찰 가치·팀 역할·변경 이유·제약을, experience는 실제 흐름·화면·측정과 한계를, arch는 최종 코드·배포/복구를, development는 AI 검토·수정·재시험 이력을 맞춘다. README는 팀 관리 docs 7개·정책·실행 근거·실제 C·미검증을 연결한다. 8종의 빈 템플릿·잘못된 예시·끊어진 링크는 정리하되 이력·정책 원문은 고치지 않는다.
6. 승인된 경우에만 문서·근거를 `docs: G7 final (test C=<C7>)`로 커밋해 **D**를 만든다. `git diff --name-only <C> <D>`가 README·문서·근거뿐인지 확인한다. docs 아래여도 AC·정책·시험 조건 변경은 단순 문서 변경으로 간주하지 않고 영향 분석·재시험한다. 실제 시험 SHA를 D로 바꾸지 않는다.
7. push는 별도 승인 범위에서만 한다. 승인받아 공개했다면 원격 main SHA와 D가 일치하는지 확인하고 전체 40자 SHA를 보고한다. 미승인이라면 로컬 문서·근거와 공개 미실행 상태를 보고한다.
8. 릴리스 태그·포털 제출도 명시적으로 승인받은 경우만 수행한다. 릴리스마다 이 과정을 반복한다. 결과 보고는 갱신 문서·REQ/AC·TC·실제 실행·시험 C/제출 D·미검증·남은 조치만 짧게 적는다.
