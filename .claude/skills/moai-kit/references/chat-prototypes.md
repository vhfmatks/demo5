# 채팅 요구사항 → HTML 3안 → 선택

많은 설정을 먼저 고르게 하지 않는다. 사용자는 원하는 일을 말하고 실제 화면 3개를 비교한다. 현재 세션이 설계하므로 별도 AI API·채팅 서버·새 의존성을 추가하지 않는다.

## 1. 요구사항 정리

- 요구 수집과 PRD의 주인은 **moai-grill**이다. `docs/prd.md`·`docs/project-brief.md`와 세션의 확인된 요구를 입력으로 사용한다. 요구가 없거나 미확정이면 `.claude/skills/moai-grill/SKILL.md`를 읽고 같은 세션에서 기능·범위·AC를 확인하고 문서를 만든 뒤 돌아온다. 초기화 전에도 가능하며 setup을 다시 실행하지 않는다. 이미 확인된 PRD가 있으면 인터뷰를 반복하지 않는다. 명시한 init 옵션도 유지한다.
- 사용자·핵심 작업·필수 기능·데이터·공개/인증 범위를 짧게 정리한다. 불명확한 접근 권한처럼 결과를 바꾸는 사항만 묻고, 화면 설정은 추천 기본값을 고른다. 비밀번호·토큰·실제 개인정보는 받지 않는다.
- 기존 프로젝트는 `project.spec.json`·`docs/project-structure.md`와 관련 nav를 읽는다. 기존 기능은 유지하고 새 기능만 추가한다. spec이 없으면 관련 기능의 실제 입력·화면만 필요한 만큼 확인한다.
- 기능마다 아래 구분을 붙인다. 특정 기능 선택이 곧 구현 완료라는 뜻은 아니다.

| 구분 | 예 | 시안 이후 처리 |
|---|---|---|
| 기본 제공 | 로그인·RBAC 기반·감사로그·관리자 포털·KDS UI | 기존 제공 범위 재사용 |
| gen 자동 생성 | 독립 도메인의 목록·상세·작성·수정·REST·시험 | 기존 gen 경로 사용 |
| 추가 구현 필요 | 승인·겹침 방지·댓글·알림·통계·복합 화면 | 요구 기능으로 기록하고 후속 구현 |

기존 기능은 실제 코드에서 확인한 범위만 “이미 제공”이라고 표시한다.

## 2. 동일한 요구 기능으로 시안 정확히 3개

1. HTML 작성 전 [KDS 화면 기준](kds.md)을 읽고 프로젝트의 `docs/design-system/README.md` → `docs/conventions/ui.md`를 따른다. 신규 프로젝트에 문서가 없으면 base에서 해당 문서와 KDS 리소스·해당 templates/examples만 별도의 빈 임시 폴더에 추출한다. 초기화·설치·DB 변경은 하지 않는다.
2. scratchpad에 `option-1.html`·`option-2.html`·`option-3.html`과 대응하는 `option-1.spec.json`~`option-3.spec.json`을 만든다. 사용자에게 보여 주는 산출물은 HTML이며 spec은 선택 후 생성용이다.
3. 세 안의 필수 기능·도메인·필드·접근 범위는 동일하다. 정보 배치·탐색·목록 표현·작업 동선은 실질적으로 다르게 한다. 예: 표 중심 빠른 처리 / 목록·상세 나란히 / 단계별 입력 중심. 서비스에 맞게 구성하고 색만 바꾸지 않는다. `PRESETS`는 참고용이며 프리셋 때문에 공개 범위나 필수 기능을 바꾸지 않는다.
4. HTML은 서비스 용어와 합성 데이터로 핵심 작업·목록·상세·입력을 보여 준다. HTML 안에서 최소 vanilla JS로 화면 전환·검색·폼 시연을 제공한다. React·Next·API 호출·실제 저장은 사용하지 않고 “프로토타입 · 합성 데이터 · 실제 저장 없음”을 표시한다. 업무 처리 결과는 모의 결과라고 명시한다.
5. 기존 `public/kds` 또는 `assets/base.tgz`의 KDS 20261012 CSS 3종(tokens → base → components)·필요 SVG와 해당 template/example의 배치를 사용한다. 입력·버튼·표·GNB를 작게 줄이거나 kds 클래스를 다시 정의하지 않는다. HTTP 미리보기로 열어 CSS 상대 경로 SVG가 정상 표시되도록 한다. 파일 단독 제출 요청이면 필요한 SVG를 인라인으로 묶는다. KT Flow 파일·외부 CDN·외부 폰트 요청은 포함하지 않는다. 사용자 문자열은 textContent 또는 HTML 이스케이프로 삽입한다.
6. 360·1280 폭에서 넘침 없는 반응형, 입력 라벨, 키보드 포커스, 읽을 수 있는 상태 문구를 유지한다. 폼 시연에서 비밀번호·결제정보 등 민감정보 입력을 요구하지 않는다.
7. 각 HTML에 시안 이름·차이·요구 기능 목록과 제공 구분을 표시한다. 추가 구현 기능도 눈으로 확인할 수 있게 시연하되 자동 생성 범위와 구분한다. 기능 커버리지·추가 구현 목록은 별도 `requirements.md`에 짧게 남긴다. spec의 임의 키에 넣지 않는다(`checkSpec` 정규화가 버린다).

## 3. spec 검사와 제시

- `scripts/survey/catalog.mjs`의 `checkSpec`·`DEFAULT_CHOICES`·`PRESETS`를 재사용한다. 필드 문법은 `references/fields.md`를 따른다. 신규 spec의 name/title에는 사용자가 지정한 `--name`/`--title`을 반영한다(CLI는 spec 값을 우선한다). 오류가 있는 spec을 사용자에게 선택안으로 내지 않는다.
- 기존 프로젝트는 기존 이름·제목·도메인을 보존한다. 새 도메인 충돌·참조 대상은 기존 survey 검증 조건과 동일하게 확인한다. 관련 CLI 로직을 복제하지 않는다.
- HTML과 대응 spec의 navigation/theme 및 화면 지침이 일치하는지 확인한다. 실제 자동 적용은 navigation/theme와 gen CRUD다. 다른 화면·업무 기능은 후속 구현 지침이며, HTML 그대로 앱이 완성된다고 약속하지 않는다.
- HTML 3개를 열 수 있는 경로/링크와 `번호 | 시안 이름 | 작업 방식 차이` 3행만 안내한다. 파일만 요청한 경우 외부 게시하지 않는다. 그 외 게시 여부는 세션의 Artifact 규칙을 따르며 로컬 디자인 리소스·제한된 글꼴을 무단 배포하지 않는다.
- “1·2·3 중 하나를 고르거나, 원하는 수정점을 말씀해 주세요”라고 안내하고 선택을 기다린다. 사용자가 요구 기능을 말한 것만으로 특정 안을 선택했다고 간주하지 않는다. 수정 요청은 해당 HTML·spec·기능 기록을 함께 갱신하고 다시 보여 준다. 기능·권한·범위·AC 변경이면 먼저 grill 절차로 해당 PRD 항목을 확인·갱신한다. 배치만 바뀌면 요구 인터뷰는 반복하지 않는다.

## 4. 선택 후 기존 생성 경로 사용

- 선택 전 프로젝트 초기화·의존성 설치·DB 변경·현재 `project.spec.json` 덮어쓰기는 금지한다. 미리보기 폴더만 만든다.
- 신규: `K init <dir> --spec=<선택파일> --dry-run`. 기존: 프로젝트 루트에서 `K survey --spec=<선택파일> --dry-run`. 경로는 셸 규칙에 맞게 인용한다. 요구사항에 포함된 자연어는 CLI에 전달하지 않는다.
- 계획과 “자동 생성 / 후속 구현” 차이를 짧게 보여 준다. 사용자가 시안 번호만 고르면 아직 적용하지 않는다. “2번으로 만들어 줘”처럼 적용 의사까지 명시했거나 별도 확인받은 뒤에만 같은 명령에서 `--dry-run`을 빼고 실행한다. 사용자가 명시한 `--dry-run`은 제거하지 않는다. dir·name·title·no-install 등 기존 요청 옵션을 유지한다.
- 선택한 spec 하나만 적용한다. 기존 CLI가 spec·`docs/project-structure.md`를 갱신하고 도메인별 gen을 실행한다. 기능 기록은 후속 구현이 잃지 않도록 `docs/project-structure.md`에 추가 구현 목록으로 부분 반영한다. 실제 구현은 기존 이슈·gen 절차를 따른다.
- 기존 미커밋 변경을 보존한다. 적용 실패는 그대로 보고하고 기존 재개 경로를 사용한다. 생성 명령 종료 전에 성공·설치 완료라고 하지 않는다.
- 고급 설정을 직접 편집하려는 사용자에게만 `/moai-kit survey --advanced` 또는 신규 `/moai-kit init --survey`를 안내한다. `--advanced`는 스킬 전용이며 CLI로 전달하지 않는다.

## 확인 시나리오

- 신규: “회의실 예약 서비스. 예약 작성·수정·취소와 시간 겹침 방지가 필요해. HTML 3개만 보여 줘.” → 같은 기능의 3안, CRUD/겹침 방지 구분, 유효한 spec, 선택 전 생성 없음.
- 기존: “기존 요청 게시판에 댓글·처리 알림을 추가하고 싶어. survey로 시안부터 보여 줘.” → 기존 기능·접근 범위 보존, 댓글·알림 추가 구현 표시, 3안 제시 후 대기.
- 선택: “2번” → dry-run 계획까지만. “2번으로 만들어 줘” → 계획 확인 후 선택한 spec만 적용. `--dry-run` 요청이면 적용하지 않는다.
